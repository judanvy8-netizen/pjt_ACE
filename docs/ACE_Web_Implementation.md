# ACE 웹서비스 구현 및 검증 기록

작성일 2026년 11월 13일 · 대상 `ACE_Web_Project.zip`

## 1. 계획 반영 현황

| 항목 | 구현 내용 | 검증 상태 |

| 이력과 정답 | MySQL 6개 테이블, 입력·예측·개체 저장, 정답 버전과 평가 이력, 오답 필터 | 구현 소스와 SQL 포함. MySQL 8.4 통합 실행 필요 |
| 제출본 분석 | 제출 CSV로 만든 사진 마릿수 오답 9장과 개체 품종 비교표 | 31/40장과 27/50마리 재계산 |
| 기존 Python 호환 | main-2 전처리·검출·분류·박스 보정 공용화. 기존 CLI와 같은 출력 CSV 열 및 기본 결과 폴더 | 핵심 함수 11개의 구문 구조가 제출본과 같음을 확인. 실모델 비교 필요 |
| 오류 처리 | 이미지 용량·경로, 추론 실패, DB 장애, 같은 실행 재시도 | Python 경로·오류·재시도 모의 확인. Java·DB 오류는 통합 확인 필요 |

전환계획서가 다음 PDCA 주기로 둔 웹캠, 동영상, 일괄 웹 업로드와 36/40 개선 모델 검증은 후속 범위다. 36/40 개선 소스와 실행 조건은 제공된 기준 ZIP에서 확인되지 않았다.

## 2. Spring MVC 요청과 저장 흐름

| 경로 | 용도 |
| --- | --- |
| `GET /`, `POST /analyze` | 업로드 화면과 사진 분석 |
| `GET /history`, `GET /history?filter=errors` | 최근 200건, 그중 최신 정답 기준 오답 보기 |
| `GET /history/{runId}` | 원본·결과, 예측, 정답 버전, 평가 |
| `POST /history/{runId}/truth` | 마릿수 정답과 선택 개체 정답 저장 |
| `POST /history/{runId}/retry` | 기존 실행 ID로 분석·결과 저장 재시도 |
| `GET /media/{runId}/{kind}` | DB에 연결된 원본 또는 결과 이미지 |
| `GET /benchmark` | 제출 시점의 검증표 |
| `GET /api/runs/{runId}` | 40장 비교 도구가 사용하는 예측 조회 |
| Python `GET /api/health`, `POST /api/infer` | 모델 준비 상태와 단일 사진 분석 |

`analysis`는 분석 흐름, `media`는 파일과 입력 메타데이터, `truth`는 정답 버전과 평가를 맡는다. 각각의 Controller가 HTTP 입력을 받고 Service를 호출한다. Repository가 Spring JDBC로 DB를 읽고 쓰며, Entity는 DB 행을 Java record로 표현한다. DO는 업로드, Python 응답, 상세 화면, 정답 폼 등 계층에서 필요한 데이터를 전달한다.

1. Spring은 UUID를 만든 뒤 `inbox/<run_id>/original.<확장자>`에 파일을 쓴다. 입력과 `PENDING` 실행은 하나의 DB 트랜잭션으로 생성한다.
2. FastAPI는 공유 폴더에서 해당 사진을 읽고, 모델 3개를 프로세스 내에서 재사용한다. 동일 실행 ID에 대한 재시도는 저장된 분석 JSON과 결과 이미지를 재사용한다.
3. Spring은 실행 행을 잠근 상태에서 분석 결과와 검출 객체를 한 트랜잭션으로 저장한다. 이미 성공한 실행은 같은 ID로 다시 저장하지 않는다. 처음 DB에 등록한 뒤 결과 저장이 실패하면 이력에서 재시도할 수 있다.
4. 정답이 입력되면 현재 분석은 유지하고 새로운 정답 버전과 평가를 저장한다. 마릿수 오차는 종류별 절대값으로 계산한다. 품종 평가의 분모는 입력한 정답 개체 수이며 미검출과 종 오류를 포함한다. 비교 대상은 사람이 사진 위치와 박스 번호로 연결한다.

## 3. MySQL 데이터 관계

| 테이블 | 관계와 주요 데이터 |
| --- | --- |
| input_media | 입력 파일과 원본 경로. 실행 UUID로 중복 방지 |
| analysis_run | 입력당 1회 실행. 상태, 마릿수, 결과 경로, 처리 시간, 모델 SHA-256과 설정 |
| detected_pet | 실행당 0개 이상. 박스 번호·좌표, 검출·분류 점수와 품종 후보 |
| ground_truth | 입력별 여러 버전. 버전과 종류별 정답 마릿수 |
| ground_truth_pet | 정답 버전별 개체. 종류·품종·위치, 연결 박스와 비교 결과 |
| evaluation | 실행과 정답 버전의 평가. 종류별 마릿수 오차, 품종 일치 집계 |

## 4. 실행으로 확인한 항목

- Python 소스 문법 검사를 통과했다.
- FastAPI 테스트 클라이언트와 대체 추론기로 상태 조회, 정상 0/0, 같은 ID 재요청, 경로 이탈, 심볼릭 링크, 없는 파일, 손상 입력 응답, 15MB 초과 응답을 확인했다.
- 기존 정답표·결과 CSV를 재계산해 마릿수 31/40장, 개체 품종 27/50마리를 확인했다.
- Java 소스는 Java 17 문법 모드로 파싱했다. 이 검사는 Gradle 의존성 컴파일과 Spring 실행을 포함하지 않는다.

## 5. 학생 PC에서 남은 인수 확인

1. README의 DB 생성·Python 설치·Gradle 빌드를 새 폴더에서 실행한다.
2. 개만, 고양이만, 둘 다, 대상 없음의 사진을 각각 업로드한다. 원본과 결과 이미지가 열리는지 확인한다.
3. 정답 미입력, 대상 없음의 0/0, 정답 수정, 품종 개체 매칭과 오답 필터를 확인한다. 재시작 후 이력을 다시 연다.
4. 깨진 이미지, 잘못된 확장자, AI 서버 중단, MySQL 중단, 같은 실행 재시도를 확인한다.
5. `scripts/compare_web.py`로 사진 40장을 비교한다. CLI와 웹의 사진별 마릿수와 개체별 품종·분류 상태 일치를 확인한다. T18·T31·T39의 종 오류와 T25·T33·T34의 다중 객체 사례를 따로 살핀다.

검토 환경에서 Gradle 배포 파일을 내려받을 수 없었고 MySQL 8.4와 PyTorch·OpenCV·Ultralytics 실행 환경이 준비되지 않았다. 따라서 Spring 빌드, 실제 모델 추론, MySQL과 연결한 브라우저 동작 및 40장 전체 재현은 인수 확인 단계에 남아 있다.

## 6. DB 설계 자료

LOOK의 개념도, 물리 ERD, Excel 정의서 형식을 참고했다. ACE 사진 분석 스키마의 6개 테이블, 52개 컬럼, 외래키 6개를 반영했다.

- `GET /db-design`은 `design.controller.DatabaseDesignController`에서 처리한다.
- `templates/database-design.html`에서 개념·물리 다이어그램, 키 관계, 컬럼과 JSON 항목을 조회한다.
- `static/db-design`에 한글 개념 ER PNG, 물리 ERD PNG, Excel 정의서를 포함했다. Excel에는 물리 컬럼과 JSON 항목을 각각 담았다.
- 관계와 컬럼을 소스 DDL에서 추출했고, Excel 저장본을 다시 읽어 컬럼과 자료형을 대조했다. 실제 MySQL의 운영 메타데이터 확인은 학생 PC의 DB 초기화 후 진행한다.
