## 구현 흐름

`benchmark`의 Repository는 CSV와 이미지 파일을 읽고 Service는 마릿수 일치와 버전별 변화를 집계한다. 웹 신규 분석은 기존 `main-2` 기반 FastAPI를 호출한다. 업로드 화면의 JavaScript는 `POST /api/analyze-photo`로 사진을 한 장씩 보내고, 실행 ID가 만들어진 실패는 `POST /api/runs/{runId}/retry`로 재시도한다. 장당 크기 제한은 기존 값인 15MB를 적용했다.

정답 검수는 `ReferenceTruthService`가 기존 실행의 원본과 기준 사진을 비교한 뒤 상세 화면에 초안을 전달한다. CSV의 품종·위치 서술은 검수 참고 자료로 보여준다. 사용자가 품종 평가를 원하면 개체별 정답에 박스 번호를 수기로 연결한다. 정답을 저장하기 전까지는 ‘검수 대기’이며, 기존에 저장한 정답이 있으면 해당 정답이 우선한다. 이번 수정에는 DB 테이블 변경이 없어 1차 DB의 이력을 사용할 수 있다.

## 확인 결과

- Java 비교 로직을 제공된 CSV에 실행해 28/40, 28/40, 31/40을 확인했다. 개선·새 오답 수는 main→main-1에서 2장·2장, main-1→main-2에서 3장·0장이었다.
- T29의 고양이 예측은 3·3·2마리로 비교됐다. 버전별 결과 이미지 파일도 확인했다.
- CSV의 BOM, 인용된 쉼표·줄바꿈, 잘못된 열 수, 중복·누락 행을 확인했다. 비교 이미지 경로의 허용 범위도 확인했다.
- 기준 이미지 일치, 동명 다른 파일, 미등록 이미지, 기준 정답 0/0을 Java 로직에서 확인했다. 이 검사는 Spring과 파일 저장 의존성을 대체한 환경에서 진행했다.
- Java 17 문법, Python 문법, 배치 JavaScript 문법을 점검했다. 모의 서버 응답으로 정상·실패·정상 순서의 계속 처리와 동일 실행 ID 재시도를 확인했다. 제공 영상이 프로젝트에 같은 바이트로 복사됐고, H.264/AAC 1280×720, 약 10초임을 확인했다.
- 실행 환경의 네트워크에서 Gradle 배포 파일 다운로드가 실패했다. 따라서 Spring 전체 빌드와 Thymeleaf 렌더링, MySQL 연동, 실제 AI 추론을 통한 복수 업로드는 Windows 실행 후 확인한다.

## Windows 인수 확인

1. README의 빌드 명령을 다시 실행하고 홈의 영상 재생과 메뉴 이동을 확인한다.
2. 버전 비교에서 40장의 집계 수치와 T29의 이미지 4장을 연다.
3. 정상 사진 2장과 손상된 JPG 1장을 같은 요청 목록에 선택한다. 정상 2건이 저장되고 오류 사진은 실패 표시가 나오는지 확인한다.
4. 기준 원본, 같은 이름의 다른 사진, 미등록 사진, 0/0 정답을 열어 초안 표시를 확인한다.
5. 검수 완료 후 정답을 수정하고 서버를 재시작한다. 기존 이력과 두 정답 버전이 보이는지 확인한다.
